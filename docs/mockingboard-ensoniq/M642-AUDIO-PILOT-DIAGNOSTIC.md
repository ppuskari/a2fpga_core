# M6.4.2 HDMI Audio Pilot — audio-only dropout isolation

**Branch:** `petar/mb-doc-m642-audio-pilot-20261114`  
**Parent:** `petar/mb-doc-m641-coherent-20261113`  
**Status:** FPGA diagnostic implementation committed. Icarus/CI verifies pilot; Gowin route and real hardware remain to be done.

## Evidence and rationale

With coherent MCS R0..R14 publication enabled and M6.4 de-clicker active, Sugar Plum musical detuning and many inter-note clicks improved, but a captured 44.1kHz HDMI WAV showed multiple **~0.9–1.02 second exactly-zero stereo audio dropouts** at variable musical positions. The HDMI **video stays solid** throughout. Gowin post-route STA reported **no violated setup/hold endpoints** and +1.353ns worst 54MHz setup slack under supplied constraints. Those observations do not yet establish whether the silence is generated by DOC/music logic or introduced by the HDMI audio transport/capture.

This build adds one very quiet pilot on **only the RIGHT** final HDMI PCM channel. The pilot is inserted **after** the shared DOC audio core, speech/music mixer, CDC, `audio_out` resampler and final -2dBFS limiter. It uses only the existing one-cycle `clk_audio_w` sample strobe and `clk_pixel_w`, never the old video debug overlay.

### Pilot specification

- 44.1kHz audio sample strobe / 44 samples per period = **1002.27Hz** square.
- Amplitude **+/-256 signed PCM** (about **-42.1dBFS peak**), right channel only.
- Left channel is byte-for-byte unchanged at the final PCM input to HDMI.
- Right sum is clamped to **+/-26028**, retaining the original -2dBFS output ceiling.
- Opt out by setting top-level `MB_DOC_HDMI_AUDIO_PILOT_ENABLE=1'b0`; the synthesis then removes the pilot logic.
- Does not load the CPU, BL616, SDRAM, audio FIFO, FPGA video overlay, DOC oscillator or PCM sample bank.

### Static configuration

```systemverilog
parameter bit MB_DOC_FX_AY_BYPASS_ENABLE = 1'b0,
parameter bit MB_DOC_DECLICK_ENABLE = 1'b1,
parameter bit MB_DOC_COHERENT_PUBLISH_ENABLE = 1'b1,
parameter bit MB_DOC_HDMI_AUDIO_PILOT_ENABLE = 1'b1,
```

`DebugOverlay.ENABLE(1'b0)` remains disabled.

## Test sequence

1. Preserve your last stable M6.4 and M6.4.1 bitstreams, and check Gowin post-route STA on the new branch. This diagnostic does not promise that resource placement and timing will match.
2. Build FPGA only. **Do not reflash BL616.**
3. Play Sugar Plum for three or four repeats (2–3 minutes), recording a stereo 44.1kHz WAV from the same HDMI/optical path as previous tests. The right channel should have a faint ~1002Hz background tone even when the piano is at rest. If no pilot at all, verify bitstream and output path.
4. During one of the original ~1-second dropouts, inspect the spectrogram or zoom right-channel PCM around the silent area.

| What remains during apparent dropout? | Interpretation |
|---|---|
| Right pilot continues, left music disappears | HDL HDMI transmission/capture is alive; DOC/music/resampler path is the main suspect |
| Right pilot vanishes and both channels are digital zero | HDMI audio transport, packetization, clocking/reset, or capture apparatus downstream of pilot |
| Right pilot continues and right music disappears | Strong evidence music generation upstream of the pilot failed |
| No dropout observed after multiple repeats | Inconclusive; the problem is intermittent. Repeat or revert A/B |

Pilot presence/absence alone cannot distinguish DOC from `audio_out` resampling; that comes in a future narrower build after finding the broad fault boundary. The pilot does NOT cure the missing notes; it marks which side fails.
